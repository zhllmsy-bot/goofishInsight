## 1. 文档目的

这份文档用于回答一个更根本的问题：

`Goofish Insight 到底要做成什么产品，后续架构和页面应该围着什么目标转。`

本项目的产品目标不是泛化的“闲鱼采集平台”，也不是“内部监控看板”。

本项目要做的是：

`一款靠谱的二手商品价格指导助手。`

这里的“靠谱”不是 UI 观感，而是指：

- 价格对象定义正确
- 样本口径稳定
- 价格证据可解释
- 无法可靠定价时明确拒绝给价
- 价格、走势、机会判断都能被人工复核

这份 PRD 会作为后续三类工作的共同约束：

1. 数据和聚合逻辑
2. API 和运行链路
3. 页面和交互设计

## 2. 北极星定义

### 2.1 产品北极星

帮助操作者在目标品类中，稳定看清：

- 某个核心属性组合的二手合理价格
- 该价格近期的变化趋势
- 当前挂牌相对这个价格是便宜、合理还是偏贵

### 2.2 产品第一原则

`价格必须对应一个明确的可定价模板，而不是模糊的型号名称。`

举例：

- 错误对象：`Mac mini / M4`
- 正确对象：`Mac mini / M4 + 16G + 256G`

对于 Garmin、相机、镜头、手机等品类也同理。

### 2.3 产品成功标准

当用户看任一价格结论时，系统必须同时回答：

1. 这个价格对应哪个模板
2. 这个模板的样本和走势是否足够可靠
3. 当前挂牌相对该模板价格便宜了多少或贵了多少

如果任一问题答不清，系统应优先输出“不足以指导”的状态，而不是硬给价格。

## 3. 核心用户与核心任务

### 3.1 核心用户

- 二手买手
- 选品研究人员
- 价格校准人员
- 内部运营和策略制定者

### 3.2 核心任务

用户最关心的不是“系统跑得怎么样”，而是：

- 这个型号下，哪些规格真正值钱
- 某个规格现在的合理收货价是多少
- 这个规格最近是在涨、跌还是横盘
- 当前新出的挂牌里，哪些相对它偏便宜
- 这个价格结论有多可靠

## 4. 产品问题陈述

当前系统已经具备很强的采集、审查、规格抽取、价格聚合和看板能力，但仍存在一个核心错位：

`系统默认把“型号”当成价格单位，而不是把“模板属性组合”当成价格单位。`

这会导致两个直接问题：

1. 不同核心规格被混合计算，价格失去业务意义
2. 页面虽然信息很多，但不能直接回答“这个具体配置现在值多少钱”

因此，本产品下一阶段不应继续以“页面增量优化”为主，而应围绕“价格对象重构”推进。

## 5. 产品原则

### 5.1 模板优先，不是型号优先

价格指导的基本单位必须是 `Priceable Template`，定义为：

`型号 + 对该品类足以决定主价格的核心属性组合`

### 5.2 给价必须带证据

每一条价格线至少必须附带：

- 样本数
- 独立卖家数
- 最近活跃时间
- exact spec 覆盖率
- 置信等级或可靠度分
- 对应趋势窗口

### 5.3 可以不给价

以下任一条件不满足时，系统可以且应该不给出明确价格带：

- 模板属性未选完整
- 样本数不足
- 卖家分散度不足
- spec 提取置信度不足
- 最近活跃度不足
- 校准锚点不足

### 5.4 先价格结论，再证据，再原始数据

所有用户页面都应遵循：

1. 当前模板价格
2. 趋势与结论
3. 当前挂牌相对模板的偏离
4. 证据与原始明细

### 5.5 技术视角退后，但不消失

模型 trace、请求日志、运行状态等内容仍然重要，但它们应进入自己的上下文页面，不占用价格判断的主工作区。

## 6. 核心产品对象

产品中需要明确区分 4 层对象：

### 6.1 品类 Category

例如：

- Apple 电脑
- Garmin 手表
- 相机机身
- 可换镜头

### 6.2 型号 Product Model

例如：

- Mac mini / M4
- Mac Studio / M2 Ultra
- Fenix 7X
- RF 70-200 F2.8

### 6.3 可定价模板 Priceable Template

这是价格的主对象。

例如：

- `Mac mini / M4 + 16G + 256G`
- `Fenix 7X + 51mm + Solar`
- `RF 70-200 F2.8 + RF 卡口 + 二代`

### 6.4 挂牌修正因素 Listing Adjustment Factors

这些因素影响单条挂牌的实际判断，但不定义主模板价格：

- 成色
- 配件是否齐全
- 发票和保修
- 电池健康
- 颜色
- 箱说
- 本地面交 / 异地邮寄

## 7. 各品类核心定价属性

系统必须为每个品类明确区分：

- 核心定价属性
- 非核心修正因素

### 7.1 Apple 电脑

核心定价属性：

- 芯片家族
- 屏幕尺寸
- 内存
- 硬盘
- 可选时带 CPU / GPU 核心

非核心修正因素：

- 颜色
- 电池循环
- 箱说票
- 保修状态
- 成色

### 7.2 Garmin 手表

核心定价属性：

- 产品线
- 表径
- Solar / Non-solar
- AMOLED / MIP
- 代际

非核心修正因素：

- 表带材质
- 外观磨损
- 盒子配件
- 续航表现描述

### 7.3 相机机身

核心定价属性：

- 机型
- 代际
- 快门数区间
- 存储版本或特殊版本

非核心修正因素：

- 机身磨损
- 维修史
- 配件齐全度

### 7.4 可换镜头

核心定价属性：

- 焦段 / 光圈
- 卡口
- 代际
- 是否原厂 / 副厂

非核心修正因素：

- 镜片霉灰
- 对焦功能状态
- 包装与附件

## 8. 价格与走势的产品合同

### 8.1 页面允许展示价格的前提

右侧主工作区只有在满足以下条件时才展示价格线：

1. 已选定一个具体型号
2. 已选定或推断出完整核心定价属性组合
3. 该模板样本达到最小可靠性门槛

否则只展示：

- 模板属性选择器
- 当前缺失的关键属性
- “暂不提供可靠价格指导”的原因

### 8.2 价格输出格式

每个模板至少输出三条线：

- 安全收货价
- 正常收货价
- 市场中位价

并附带：

- 近 7 / 30 天走势
- 样本规模
- 可靠度
- 当前活跃度

### 8.3 挂牌判断逻辑

单条挂牌的判断必须相对于其匹配模板进行，而不是相对于整个型号平均价。

挂牌页或机会流只允许输出：

- 低于安全收货价
- 落在正常收货区间
- 接近市场中位价
- 明显偏高

前提是该挂牌已匹配到明确模板。

## 9. 首页产品合同

首页的任务不是讲系统运行情况，而是快速完成一次“价格判断”。

首页必须回答：

1. 这个型号有哪些核心模板
2. 当前模板值多少钱
3. 当前模板最近怎么走
4. 今天刚出来的商品里哪些偏便宜

因此首页结构固定为：

1. 左侧：品类 -> 型号
2. 右侧顶部：模板属性选择器
3. 右侧中部：当前模板价格线
4. 右侧下部：当前模板走势与当前挂牌

首页默认不展示：

- LLM trace
- worker 运行日志
- 技术诊断明细
- 与当前模板无关的同类趋势图

## 10. 其他页面产品合同

### 10.1 LLM DevOps

任务：

- 解释模型为什么把一条挂牌识别成某个模板
- 检查 prompt / request / response / token usage
- 定位抽取和判断错误

不是价格首页的一部分，而是价格可信度的诊断后台。

### 10.2 运行控制

任务：

- 确保采集、规格抽取、review、baseline、机会刷新链路正常运行

不直接承担价格解释。

### 10.3 回刷进度

任务：

- 展示历史积压、回刷吞吐、卡点和恢复情况

### 10.4 品类开通

任务：

- 判断一个新品类距离“可给出靠谱价格”还缺什么
- 不只是“采得到”，而是“能形成模板价格”

## 11. 对现有架构的判断

### 11.1 已经走对的部分

当前系统并不是从零开始，以下方向是正确的：

- 已有 structured filter 与模板属性字段
- 已有 `product` 和 `spec` 两层定价聚合
- 已有 review gate 与价格样本门控
- 已有 calibration 思路
- 已有 buy baseline / buy opportunity 方向
- 已有属性系统文档基础

### 11.2 当前偏离目标的部分

当前最大偏差在于：

1. dashboard 默认仍以 `product` 视图为主
2. `spec` 在交互上仍像“附加筛选”，而不是“价格对象本身”
3. 前台页面仍允许在模板未完整收窄时展示价格
4. 页面信息组织仍容易让“系统运行信息”压过“价格判断”

### 11.3 结论

结论不是“推倒重来”，而是：

`保留现有采集、抽取、review、baseline、机会链路，把产品默认抽象从 product 切到 priceable template。`

## 12. 核心架构决策

### 12.1 决策 A：价格单位固定为模板

任何对外展示的价格都必须可映射到一个模板 key。

建议统一引入或强化：

- `pricing_template_key`
- `pricing_template_label`
- `template_confidence`

### 12.2 决策 B：为每个品类显式维护核心定价属性集合

建议在类目运行配置或模板配置中新增一类语义：

- `pricingKeyFields`

它不同于通用筛选字段，专门定义：

- 哪些属性构成定价模板
- 哪些属性必须选满才能给价
- 哪些属性只是辅助筛选或展示

### 12.3 决策 C：模板不完整时禁止给价

当 `pricingKeyFields` 未完成时：

- 不展示价格线
- 不计算模板趋势
- 不输出机会判断

只展示缺失字段和可选项。

### 12.4 决策 D：所有趋势必须与当前模板一致

只要用户已经选定具体模板，趋势区就只能显示当前模板的趋势，不能回退显示同类其他型号的趋势。

### 12.5 决策 E：挂牌判断必须先匹配模板

机会识别和卡片分组必须先完成：

`挂牌 -> 模板匹配 -> 模板价格比较`

而不是：

`挂牌 -> 型号价格比较`

## 13. 指标体系

### 13.1 第一阶段核心指标

- 模板级价格覆盖率
- 模板级价格可靠率
- 模板级趋势可用率
- 模板匹配成功率
- 机会命中人工认可率
- 无法可靠定价时的拒绝准确率

### 13.2 第二阶段反馈指标

- 用户查看模板后打开商品详情率
- 查看详情后联系卖家率
- 联系后实际成交率
- 成交后 ROI 估计
- 人工纠错后的模板回写收益

## 14. 阶段路线

### Phase 0：产品合同冻结

冻结以下共识：

- 价格单位是模板，不是型号
- 模板不完整不允许给价
- 首页任务是价格判断，不是系统诊断

### Phase 1：模板定价模型收口

- 为各品类补齐 `pricingKeyFields`
- 统一 `product -> template -> listing` 三级关系
- 明确模板级 baseline 生成口径

### Phase 2：模板级页面收口

- 首页右侧改为模板属性面板
- 模板完整后才显示价格线和趋势
- 挂牌流只显示与当前模板相关商品

### Phase 3：可信度收口

- 在页面中明确展示样本、活跃度、可靠度和 calibration
- 允许“不足以指导”的空状态成为正式输出

### Phase 4：反馈闭环

- 人工纠正模板匹配错误
- 人工纠正价格偏差
- 反馈进入 baseline 和模板规则校准

## 15. 非目标

当前阶段暂不追求：

- 全站所有闲鱼商品的万能估价
- 自动成交或自动砍价
- 用单一模型替代人工价格判断
- 依靠 UI 包装掩盖底层价格对象错误

## 16. 决策检验问题

后续任何新接口、新页面、新分析逻辑上线前，都必须回答以下问题：

1. 这里展示的价格到底对应哪个模板
2. 模板核心属性是否已选完整
3. 样本和可靠性是否足以支持给价
4. 当前走势是否真的是该模板走势
5. 当前挂牌是否与该模板正确匹配

如果其中任一问题不能明确回答，则该设计不应进入默认用户路径。

## 17. 最终结论

本项目当前不是没有方向，而是需要把方向更明确地拧正。

现有系统在采集、规格抽取、review、baseline、机会识别上已经积累了足够多的正确能力。

下一阶段的关键不是继续堆页面或继续强化运维视角，而是把以下一句话变成整个系统的总合同：

`只对明确模板、且证据足够的二手商品给出价格指导。`

这句话一旦成立，后续页面、接口、数据模型、校准和提醒链路都会自然对齐。
